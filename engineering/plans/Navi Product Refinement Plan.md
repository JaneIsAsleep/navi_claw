# Navi Product Refinement Plan

创建：2026 年 10 月 2 日。更新：2026 年 10 月 3 日。用途：后续 Codex 开发阶段的产品设计与验收依据。

本阶段只完善产品计划。Navi 代码、配置、权限策略和个人数据均未修改，本文中的未来行为尚未实现。主导航、首页、D01 至 D08 及 Q01、Q02 均已由用户确认，见第 7 节。删除副对话时一并取消相关提醒；封存期间提醒转发主对话。目前没有阻塞本计划的待定产品方向，产品方向确认与开发授权分别处理。

依据为 [engineering/reviews/Navi UX Audit Report.md](<../reviews/Navi UX Audit Report.md>)、[engineering/plans/Navi_plan.md](Navi_plan.md)、[engineering/design/DESIGN.md](../design/DESIGN.md)、当前实现，以及本轮实际操作的本机 Muse。审查报告记录过去的观察；本轮用户决定覆盖其中与新方向冲突的建议。本轮 Muse 操作记录在第 4 节，区分界面实测与 Muse 自述，不采用其私人内容作为 Navi 数据。

## 1. 产品重构原则

Navi 的长期价值应来自准确接回交代过的事、按约定跟进、给出可用结果，并让用户始终掌握决定权。重构首先改善使用关系和连续性，克制增加功能。

**当前核心问题。** 审查发现，11 个入口按系统模块平铺，用户要自行理解消息、任务、动态、建议和审批之间的关系。高频聊天缺少重命名、封存和删除，历史标题难以辨认，省略号直接触发压缩。建议、更新和成果离开原话题后缺少接续入口；部分空状态要求先理解 Heartbeat 和工作流。状态反馈也存在断点，例如停用来源仍显示刷新成功、不同页面的同名按钮行为不同。这些是审查证据支持的问题，尚不能据此断言真实留存率。

**重构目标。** 打开即可交代或继续一件事；看到变化时理解它与自己的关系；需要决定时能检查具体行动；结果出现后能取用并继续。用户无需先学习作业、Outbox、模型协议和调度机制，也无需主动维护多个模块才能获得帮助。

| 体验原则 | 产品要求 | 验收判断 |
|---|---|---|
| 对话优先 | 表达委托、澄清、跟进和取用结果围绕原话题 | 同一件事不必跨页重复说明 |
| 下一步清楚 | 当前状态给出一个主要操作；没有事时保持安静 | 用户知道现在能做什么，或知道无需处理 |
| 上下文连续 | 保留草稿、阅读位置、真实关联和引用 | 看完更新、目标或成果可以接回相关讨论 |
| 信息有归属 | Feed、提醒、跟进和审批各有明确目的地 | 当前打开的页面不会改变投递目的地 |
| 控制可发现 | 菜单靠近对象，键盘和触屏均可发现操作 | 无需猜图标，也无需依赖鼠标 hover |
| 状态可信 | 生成、保存、批准、执行、投递分别表达 | 未执行、失败和仅获批均不会显示完成 |
| 管理负担适量 | 低频管理按需展开，日常委托自然形成必要记录 | 用户少做整理、关联和系统配置 |

**需要保持。** 保留本机运行、Python/FastAPI/SQLite、React、真实 DeepSeek、CLI 与 Web 共用 Gateway 和持久状态。保留中文文字、浅色阅读面、稳定输入区、中文组合输入保护、取消、真实空状态、来源与时间、记忆逐条参与控制和真实下载。

权限规则继续有效：普通站内提醒按已有授权自动投递；外部行动与高影响操作执行前审批；严格逐条通知策略继续保留。只有获准结果进入 Outbox，拒绝不得执行，修改动作后重新审批。导航和呈现位置改变不会降低这些要求。

本机运行边界在相关场景解释：关闭浏览器不会停止服务；电脑休眠期间不能实时执行；模型调用会发送该次有效上下文。连接、预算和运行失败需要清楚可见，无需在每条回复旁重复技术状态。

**吸收 Muse 的原则。** 保留稳定的交谈对象和受保护的主对话；专题副对话帮助接回话题；头像承接助手详情；管理操作靠近对象；Feed 安静出现；结果附带可继续讨论的上下文。这些原则适合 Navi 的个人委托和持续跟进。主导航及头像入口按用户决定对齐，内容和权限仍按 Navi 的能力定义。

**不直接复制。** 不复制 Muse 的角色素材、声音、换装、娱乐能力、影音分类和复杂并排聊天室。不把 MEMORY.md 文件编辑器搬入 Navi，继续保留逐条记忆控制。不照搬 Muse 的连接器和权限设置。Navi 形象属于自己的视觉身份，本轮规划球形入口和布局，不引入角色定制系统。

真实日历、邮件连接器另议。本轮只对齐内容组织与路由，使用 Navi 已有公开来源和本机记录。没有接入的来源不显示“已连接”，没有证据的关联不由模型补猜。

## 2. 新的信息架构

**当前。** 页面和入口来自审查报告及 [App.tsx](../../frontend/src/App.tsx)。

| 当前页面 | 当前入口 | 当前问题 |
|---|---|---|
| 对话 | 主导航、全局新对话、会话栏加号、历史行 | 新建重复；历史管理不足；更多图标语义错误 |
| 消息 | 独立主导航、未读计数、全部已读 | 投递与创建对话分开，容易丢失事情的背景 |
| 目标 | 独立主导航、添加表单、条目跟进 | 表单和记录先于自然讨论，目标与任务关系需用户理解 |
| 任务 | 独立主导航，排程与关注事项同页 | 日常提醒和技术调度混合，类型及执行指令偏工程语言 |
| 动态 | 独立主导航、来源、刷新、简报 | 来源管理突出，缺少带引用讨论，刷新反馈可能失真 |
| 建议 | 独立主导航、生成、详情 | 泛化标题、原始 JSON 依据、与当前状态的关系不明 |
| 审批 | 独立主导航、批准、拒绝、编辑 | 需离开原场景，批准与实际执行的联系不清楚 |
| 记忆 | 独立主导航、添加、编辑、启停、删除 | 参与状态有价值，来源解释和删除保护不足 |
| 成果 | 独立主导航、详情、下载、生成简报 | 可用文件与来源话题连接不足，同名按钮行为不同 |
| 活动 | 辅助导航、作业与审计详情 | 日常跟进与技术诊断混合，ID 和原始状态过多 |
| 设置 | 辅助导航、连接、行为、费用、运行说明 | 基础连接和协议等高级配置混在一起 |

**未来主导航。** 按 Muse 的核心入口与顺序保留六项：对话、搜索、动态消息、构想、目标、成果库。设置在底部辅助区域。不增加“进展”主入口。

| 主入口 | 用户来这里做什么 | 范围 |
|---|---|---|
| 对话 | 交代、继续、看相关提醒与审批 | 一个主对话，可不断新建副对话 |
| 搜索 | 找回已存在的话题 | 首轮明确为“对话标题搜索”，包含封存对话 |
| 动态消息（Feed） | 看按关注说明形成的内容与相关事项 | 混合单一信息流，按本地生成或收录顺序排列，静默更新 |
| 构想 | 理解下一步建议并决定是否采用 | 沿用建议能力，展示可读依据并连接讨论 |
| 目标 | 看持续事项及其推进情况 | 页面只包含追踪、简要目标、设定目标分类 |
| 成果库 | 找到和使用已有结果 | 沿用成果与下载，不增加未支持的影音类目 |

桌面使用窄图标栏。导航名称在 hover 和键盘聚焦时出现，按钮始终有无障碍名称和选中状态。触屏通过可见名称或展开入口识别，点击区域至少保持现有 40px 标准，首轮以 44px 为设计目标。图标栏参考 Muse 的紧凑比例，以约 72 至 80px 作为桌面设计起点，在 1280px、375px 和 320px 验证实际空间。

**助手身份入口。** Navi 的专属形象作为球形按钮。非对话页面放在左侧菜单栏最上方；进入对话后放在聊天区正上方。两种位置代表同一个助手，避免同时出现两个竞争入口。球形按钮属于页面布局，不要求拖拽、桌面悬浮窗、自动移动或动画。

点击形象后从右侧打开“关于 Navi”详情侧栏，包含四个标签：动态（跟进）、审核请求、提醒事项、身份信息。身份信息内部提供明确的“记忆”入口。这里的“动态”表示助手跟进，主导航的“动态消息”表示 Feed；副标题分别使用“跟进记录”和“关注内容”，降低重名成本。小屏改为可返回的单栏详情，保留相同层级和名称。

| 当前入口处理 | 未来归属 | 原因及保留边界 |
|---|---|---|
| 对话 | 对话主入口 | 最高频表达与接续空间 |
| 动态 | 动态消息（Feed） | 保留关注内容的独立阅读目的 |
| 消息 | 正常提醒回创建时的对话，封存期间转发主对话；旧投递记录按真实关联查看 | 删除副对话取消相关提醒；不混入 Feed，不随意创建新聊天 |
| 建议 | 构想主入口 | 与 Muse 分工一致，保留讨论与采纳边界 |
| 目标 | 目标主入口 | 保留方向与追踪，移出全量提醒配置 |
| 任务 | 头像侧栏的提醒事项；技术调度在高级详情 | 普通用户按何时做什么管理，独立提醒不强迫建立目标 |
| 审批 | 有原对话时持久内嵌回复；头像侧栏集中索引 | 无原对话的后台审批只在审核请求中出现 |
| 记忆 | 头像 → 身份信息 → 记忆 | 与助手如何理解用户的身份关系一致，保留逐条控制 |
| 成果 | 成果库主入口 | 保留取用结果的明确目的 |
| 活动 | 头像动态展示可读跟进；完整审计在设置中的运行记录 | 分层呈现，完整记录继续保留 |
| 设置 | 底部辅助入口 | 连接、授权、预算和隐私容易找到；协议等按需展开 |

**默认打开。** 恢复最近使用的有效、未封存对话，保留输入和当前草稿；首次使用进入唯一主对话。最近会话已被封存、删除或不可用时返回主对话，并在必要时说明原话题不可用。首页与 Chat 共用一个页面，不增加今日概览。

少量真实进展提示仅来自当前事情的待确认、失败或可用结果，不默认调用模型生成摘要。Feed 新帖子不会转成聊天通知。无原对话的后台审批由头像入口的待审批状态承接，不插入正在聊天的消息流。没有变化时保持安静。

**主对话与副对话。** 主对话是一个持久、唯一的日常空间，不能重命名、封存、删除或钉选。副对话用于专题讨论，可不断新建，首轮支持重命名、封存、删除，暂不增加钉选。一个副对话新建入口放在会话列表标题旁，取消重复全局新建。空白副对话编辑可先停留在本地草稿，发送首条消息后才产生历史条目，避免空会话堆积。

恢复最近副对话与主对话的唯一性可以同时成立。最近话题方便接续，主对话提供长期稳定归属。用户始终可以从历史顶部回主对话。

**概念之间的关系。**

| 概念 | 含义、归属和边界 |
|---|---|
| 对话 | 委托及上下文；临时问答无需建立目标 |
| 进展 | 一件事的真实变化，在原对话、追踪或跟进中展示；不新增实体 |
| 目标 | 持续方向及简要描述；详情承接下一步、真实成果和活动时间轴 |
| 任务 | 一次或周期执行的工作；追踪只显示实际进程，提醒事项承接时间控制 |
| 关注事项 | 待办或待检查内容；有截止日期不等于已安排提醒，沿用已有区分 |
| Feed | 关注说明形成的内容、已有来源和本机相关事项的混合阅读流 |
| 建议 / 构想 | 基于当时上下文提出的下一步；不会自动变成目标或任务 |
| 消息 / 提醒 | 已实际投递的内容；正常情况下回创建对话，封存期间发主对话，删除时取消相关提醒；未读状态附着实际消息 |
| 跟进动态 | 助手做了什么、推进到哪里、哪里需要处理；避免复制整份 Feed |
| 审批 | 对具体行动及版本作决定；位置按是否存在原对话确定 |
| 记忆 | 用户允许用于后续回答的信息；跨会话，逐条可控 |
| 成果 | 可查看、使用或下载的结果；草稿与已导出文件分开 |
| 设置 | 连接、权限、成本与运行边界；高级诊断按需进入 |

对话可以形成目标或独立提醒，目标可以关联任务，任务产生结果，结果可形成成果、建议或需要决定的行动。需要审批时先形成具体提案，获准后进入现有执行和投递流程。记忆为这些过程提供有效上下文，设置限定运行边界。

**内容与路由。** 内容归属是产品规则，需要持久关系支撑，不能依赖当前正在看的页面。

| 内容 | 主要呈现位置 | 通知与持续性 |
|---|---|---|
| 主对话创建的定时提醒 | 主对话中的实际投递消息 | 日常或严格策略照旧；切到副对话不会改变目的地 |
| 副对话创建的定时提醒 | 未封存时回创建副对话；封存期间按 Q02 发主对话 | 目的地由持久状态确定，不依赖当前打开的会话，不写入 Feed |
| 从非聊天页面明确新建的提醒 | 保存前显示归属，首轮以主对话承接 | 不从隐藏的最近会话猜测目的地，沿用时间确认和授权 |
| Feed 新帖子 | 动态消息页的同一时间流 | 静默出现，无推送、聊天插话或首页提示 |
| 有原对话的审批 | 原回复持久显示；审核请求中有同一动作的索引 | 两处状态一致，只允许执行一次 |
| 无原对话的后台审批 | 头像 → 审核请求 | 完整内容和状态在此持久显示；不进入任何聊天 |
| 已封存副对话的新提醒 | 主对话，标明来源为已封存话题 | Q02 已确认：继续运行，保留原绑定；解封后未来触发回原副对话 |
| 已删除副对话的未完成提醒 | 取消相关提醒，不再投递 | Q01 已确认：关联执行和未决动作同步收尾，不转发主对话 |

明确订阅“某来源变化时提醒我”属于用户约定的提醒，按该提醒的归属投递。仅有 Feed 帖子生成不构成这项授权。该区别保留主动助手的实用性，也减少安静阅读流的噪音。

旧数据不按标题相似或模型猜测补关联。旧会话全部保留为副对话，单独建立主对话，不自动合并历史或改写旧标题。已有任务的真实创建关系继续保留；旧记录无可验证来源时在相关详情标明“暂无关联对话”，不回填到主对话。原有历史投递记录可在提醒事项的历史详情追溯，不自动复制成新聊天消息，也不并入 Feed。

## 3. 页面结构设计

以下定义页面职责及边界，供后续开发逐项验收。页面合并只改变入口与呈现方式，持久数据和权限仍有独立含义。

| 页面 / 视图 | 页面目标与进入原因 | 核心内容 | 主要操作 | 不应出现的内容 |
|---|---|---|---|---|
| 首页 / Chat | 表达、澄清、接续委托 | 当前聊天、固定输入、Navi 形象、必要的当前进展、持久审批和结果 | 发送、停止、复制、引用讨论、查看相关结果、打开助手详情 | 功能九宫格、虚构摘要、原始工具 JSON、无原对话审批、Feed 推送 |
| 会话列表 | 回主对话或专题历史 | 固定主对话、未封存副对话、标题和实际最近时间 | 打开、新副对话、重命名、封存、受保护删除 | 钉选、全量已封存视图、重复新建、无理由空会话 |
| 搜索 | 按记得的标题找回话题 | “对话标题搜索”范围、真实匹配、时间、已封存标识、无结果说明 | 搜索、清空、打开匹配、明确解封、返回原位置 | 正文检索承诺、网络搜索、无结果时自动向模型发送查询 |
| 动态消息（Feed） | 安静阅读关注内容及相关事项 | 单一按生成 / 收录顺序排列的帖子、关注说明、来源时间与本地时间 | 阅读、查看来源、带引用讨论、编辑关注说明、管理来源 | 定时提醒、审批队列、两类内容分区、原始运行日志、未接入服务卡片 |
| 构想 | 理解建议并决定下一步 | 具体建议标题、生成时间、可读的当时依据、真实关联 | 讨论、提出修改、明确要求采纳或设为目标 | 泛化重复标题、默认 JSON、把旧依据当现状、自动安排任务 |
| 目标 | 查看方向与实际推进 | 追踪、目标简述、设定目标分类 | 查看详情、讨论、确认保存、更新下一步、暂停或完成 | 全量提醒设置、消息收件箱、Feed、审批、复杂看板、伪造完成率 |
| 目标详情 | 调整一件持续事项 | 描述、下一步、实际关联、活动时间轴、成果入口 | 继续讨论、编辑、暂停、完成、查看真实任务 | 无依据的活动和关联、对目标完成自动推断所有提醒停止 |
| 助手动态（跟进） | 查看 Navi 对交代事项做了什么 | 可读的执行、变化、结果和失败；真实来源链接 | 回相关对话或目标、查看结果、展开失败详情 | 原样复制 Feed、每次内部步骤、默认 ID 和完整审计 |
| 审核请求 | 处理待确认及追溯决定 | 全部真实待审批索引、完整行动及版本、执行状态、历史 | 批准、拒绝、编辑后重新审批、定位原提案 | 自动批准、已读代替决定、无来源提案强塞聊天、短暂 toast 充当唯一记录 |
| 提醒事项 | 管理约定何时做什么 | 单次 / 周期提醒、下次执行、归属对话、暂停状态、实际结果；已有关注事项分开标明 | 查看、设置、修改时间、暂停、恢复、查看历史或失败 | 首屏要求理解 Heartbeat、全量技术作业、把关闭页面当停止提醒 |
| 身份信息与记忆 | 了解助手如何理解用户并控制有效记忆 | 简短身份说明、明确记忆入口；记忆逐条内容、状态、时间和真实来源 | 查看、添加、编辑、启停、确认删除、回真实来源 | 文件编辑器、推断档案、角色定制系统、伪造来源 |
| 成果库 | 找到可用结果并继续使用 | 内容、生成时间、草稿 / 文件状态、真实关联、下载 | 查看、下载、回原话题、带引用修改、准备简报 | 未支持的影音类目、作业流水账、批准按钮替代下载 |
| 设置 | 完成连接并掌握运行边界 | 基础连接、真实检查结果、提醒策略、时区、预算、隐私、运行说明及高级区 | 保存、检查、调整已有策略、看完整运行记录 | 密钥回显、协议参数全部平铺、把已保存当已连接、虚构连接器 |

**聊天和历史。** 聊天顶部保留当前主题、Navi 形象和相关操作，底部输入稳定。等待、停止、超时和失败如实显示，发送过程不丢草稿。对话正文保持 16px 及现有行高作为起点，状态、时间和按钮文本必须可读。

副对话行的更多菜单在 hover 或 focus 时显示；键盘可直接进入，触屏提供稳定按钮。菜单首轮含重命名、封存、删除。主对话不出现这些管理项。关闭菜单后焦点回原按钮，菜单打开不触发模型调用。手动压缩放入有明确名称的高级操作，继续保留原始历史。

重命名保存成功才更新界面，刷新后持久，自动标题不得覆盖用户手动标题。封存移出普通历史，不删除消息、摘要、目标或成果，也不取消提醒。封存期间的获准提醒转发主对话，并标明已封存来源；保留原始绑定，解封后未来触发回原副对话，已投递历史不搬动或重复发送。打开封存搜索结果不会自动解封；用户明确解封后才重新进入历史。

不提供“已封存”页面、标签、专用筛选或全量封存列表。搜索结果只呈现匹配的封存话题。用户也可以直接说“解封某个对话”；Navi 通过同一个持久化能力处理，同名需澄清，成功后再回执，不能只在回复中声称完成。

删除副对话前显示：“此对话删除后会永久删除，且无法复原。”明确提供“取消”和“删除”，默认焦点放取消。有相关未完成提醒时，补充“此对话关联的未完成提醒也会一并取消”，列明实际受影响项。取消不改数据；确认删除时按 Q01 一并取消相关单次与周期提醒，阻止未来触发，并同步收尾由这些提醒产生的未完成执行和未决动作。成功后从历史和标题搜索移除，消息及摘要不能通过正常产品流程恢复。主对话在界面和 Gateway 两端均受保护。

删除与调度、执行、Outbox 投递必须一致：仍可停止的关联工作停止，相关待审批及尚未投递动作失效；已进入不可取消执行阶段时，显示实际状态并等它结束再完成删除。不能先移除会话后继续投递，不能让迟到结果重建已删除对话，重启后也不得恢复已取消提醒。仅处理该副对话相关提醒，保留已独立保存的记忆、目标、成果和必要执行记录，弹窗解释实际影响。

**标题搜索。** 首轮只匹配对话标题，检索有效及封存副对话，主对话也可作为匹配结果。不把最近加载的一小段列表当成全量搜索，不搜索已永久删除内容。显示清楚的无结果文案和清空入口，打开结果可回到搜索上下文。

审查中用正文“今天最想推进”搜索失败的案例，首轮仍不满足。验收只能写“范围已明确、标题匹配和无结果反馈已改善”。一周试用若反复需要按记得的正文找话题，再提出方案 B；用户明确选 B 后才实施内容检索。

**目标只保留三块。** “追踪”展示真实任务进程、必要状态和顺手的结果入口。“目标”展示持续方向及简述，点击才展开下一步、关联任务和时间轴。“设定目标”提供健康、人际关系、财务、职业、兴趣、生产力、其他分类，分类先帮助开始讨论，不直接生成目标、任务或提醒。

选择分类后进入带主题提示的聊天。用户提出目标并确认保存，界面才显示持久目标及入口。未获明确要求时不自动创建周期提醒。分类仅用于开始表达和记录方向，不增加多层分类设置。

**助手详情。** 右侧栏是跨页面可返回的局部视图。打开和关闭不清空聊天、不自动切会话，也不产生模型调用。桌面保持主内容可理解，宽度以能阅读完整审批为准；空间不足时切单栏，避免把主内容挤成窄缝。关闭后焦点回触发头像，Escape、标签切换、滚动和键盘焦点均有明确行为。

提醒事项管理单次与周期约定；已有关注事项以不同类型呈现，保留截止日期与实际排程的区别。Heartbeat 的间隔、检查类型和原始作业信息放在高级详情，启停及运行边界仍易找到。目标完成不自动取消排程，暂停排程也不等于目标完成，相关操作应解释实际影响。

身份信息提供“记忆”直达入口。记忆编辑继续沿用 Navi 的逐条模型，停用后后续调用不使用该条，过去已经发送的上下文仍存在。删除记忆使用单独的永久删除确认，不新增回收站。记住信息的实际回执附带直达该条的入口，降低嵌套层级带来的寻找成本。

**审批的两种归属。** 有原对话的提案持续内嵌在 Navi 回复中，默认展示行动、执行目标、完整内容和影响，长内容可展开。原消息和助手审核请求引用同一个动作及版本。批准后显示已批准，再显示实际执行或投递结果；拒绝保留拒绝且未执行；失败保留原因；编辑使旧审批失效并对新内容重新确认。

无原对话的后台提案以审核请求为唯一主要载体，完整正文和历史状态持久显示，不创建“后台通知对话”，也不塞入主对话。等待状态可以在头像入口提示，用户有空打开时处理。它与有来源提案共用现有权限服务，不因显示位置不同改变执行条件。

动作重复点击、两个视图同时打开、刷新或重启均不得重复执行。尚未获准的提醒正文不能作为“已投递消息”先出现在聊天中，生成结果不等于获准结果。被修改的版本不可继续按旧内容批准。

**Feed、跟进和提醒分工。** Feed 是阅读流，关注主题内容与本机相关事项按生成或本地收录顺序混排，没有两区和类型切换作为主要布局。保留源发布时间、检查时间和本地生成时间，排序不用源时间冒充生成顺序。原始资料可在来源详情查看。

“关注说明（brief）”用一段可编辑文字表达想了解的主题，修改只影响以后生成，不改写旧帖子。首轮复用已有来源刷新、简报与后台生成能力，不引入真实邮件日历、新生成服务或多个频率配置。来源暂停时说明未检查，模型失败时说明未生成；不以示例帖子填空。

跟进回答“对我交代的事做到了哪里”，只展示必要变化和结果。提醒回答“到了约定时间，需要告诉我什么”，实际内容回归约定聊天。某条 Feed 可以被讨论或由用户明确设置为提醒，但这一步不会自动发生。

**结果连接下一步。** Feed、构想、目标和成果的“讨论”先在输入区放入可检查、可移除的引用，用户发送才调用模型。存在真实来源时可返回原对话；缺关联时开启明确带引用的新讨论，不声称恢复旧上下文。保留草稿和返回位置。简报入口统一为“准备简报”，先带内容进入输入区，用户发送后开始；不再让同名按钮分别自动运行和仅填入指令。

## 4. Muse 对齐策略与验证依据

本轮实际使用本机 Muse 4.1，未更新应用。核对六个主入口、目标创建与详情、Feed 阅读和讨论、构想、成果库、助手身份及记忆、提醒与审批标签，以及通用、连接器、权限和数据控制设置。未接入服务、未改变设置、未复制私人记忆，也未执行不可恢复删除。

| 观察或操作 | 实际结果 | 证据性质及适用限制 |
|---|---|---|
| 新建专题副对话并重命名为 Navi Product Check 1003 | 新对话可输入，重命名后历史显示新标题 | 本轮实际操作；验证该副对话的创建和重命名 |
| 创建两分钟后的单次中性提醒 | 确认后，测试提醒实际出现在创建时的副对话 | 本轮实测正常副对话投递；不代表封存、删除或所有调度情形已验证 |
| 建立 Navi goal check 1003 | 目标实际出现在目标页，详情有下一步和目标活动时间轴 | 本轮实测保存及详情，未创建周期任务或连接外部服务 |
| 从“其他”目标分类开始 | 先出现目标引导，再进入附主题提示的聊天 | 本轮实测；点击分类不等于已保存目标 |
| 点击聊天顶部形象和非聊天页左上形象 | 打开右侧助手详情 | 本轮实测两种位置及同一详情层级 |
| 助手详情标签 | 动态、核可工具、近期、身分；近期含提醒，身分内含记忆 | 本轮实测入口；Navi 使用用户确认的简体名称 |
| 打开记忆 | 进入 MEMORY.md 编辑界面 | 本轮只读；Navi 保留逐条记忆，不复制文件编辑方式 |
| 阅读 Feed、编辑关注指令、点击讨论 | 时间流、面向未来的指令编辑、带引用聊天入口 | 本轮实测呈现，未改指令、未发送讨论、未核验新闻内容 |
| 查看构想与成果库 | 构想连接讨论；成果库提供内容和分类入口 | 本轮实测浏览；不把能力说明和排序按钮当作运行成功证明 |
| 浏览通用、连接器、权限和数据控制 | 低频配置集中在设置窗口 | 本轮只读，未连接、更新、导出或重置 |
| 打开副对话删除弹窗 | 明示永久移除且无法复原，提供取消与删除 | 实际打开并取消，最终删除未执行 |
| 封存测试副对话 | 成功提示出现，该行从普通历史消失 | 本轮实测封存，不证明关联提醒去向 |
| 搜索封存测试话题 | 标题与正文片段均暂未返回该话题 | 本轮未验证成功；不能写成 Muse 搜索已找回封存历史 |
| 直接请求解封 Navi Product Check 1003 | 该话题重新出现在普通历史，随后实际打开原内容 | 本轮实测解封，确认了持久结果，未仅采信回复中的成功宣称 |
| 直接询问删除后的提醒行为 | Muse 再次表示删除后的调度规则没有定义 | Muse 自述，不能证明取消、继续或实际丢失 |
| 询问封存后的提醒行为 | Muse 自述定时消息重定向主对话 | 实际送达尚未确认；用户已将此方向确认为 Navi 的 Q02 规则，Muse 验证空缺仍保留 |

Muse 的审批标签本次没有新的待审项目。本轮未制造外部操作审批，也未验收完整批准、拒绝和修改链路。Navi 内嵌审批及后台侧栏规则来自用户决定，后续需在 Navi 上独立验证。

研究结束时，测试副对话已解封，测试目标保留，均未永久删除。测试提醒只要求单次，没有新建周期提醒；两分钟的正常投递已观察到，其余封存路由测试未形成送达证明。助手提醒标签中未显示这些测试为当前待提醒项，该现象也不足以判定已经取消或转发成功。

用户要求“删除副对话后，未完成提醒会取消还是继续运行？”已直接追问；Muse 的回答仍无法确定。助手声称“检查规则”提供的是自述，不可代替真实删除后的运行证据，删除弹窗也未说明提醒处理。用户随后为 Navi 明确选择 Q01：一并取消相关提醒。该选择是 Navi 的产品规则，不代表 Muse 的删除行为已验证。Q02 同样已确认采用封存期间转发主对话，实际实现与投递仍须在 Navi 独立验收。

| 采用的原则 | 对 Navi 的适配与理由 | 保留的边界 |
|---|---|---|
| 聊天中心 | 默认最近对话，唯一主对话与专题副对话承接不同持续性 | 不强迫所有问题建立目标 |
| 历史管理 | 副对话可重命名、封存、永久删除，标题和最近时间可辨认 | 首轮不钉选，不暴露全量封存界面 |
| hover 操作 | 行尾和消息操作在对象附近出现，降低默认视觉密度 | focus 与触屏都有等效入口 |
| 隐藏低频操作 | 身份记忆、调度细节、手动压缩和协议按需进入 | 执行目标、审批正文、拒绝和停止不隐藏 |
| 上下文连续 | 真实关联、持久引用、草稿和返回位置连接页面 | 不按标题猜关联，不复制完整双聊天室布局 |
| 结果与下一步连接 | 保存、投递和导出后提供对应内容与讨论入口 | 未保存、未获准、未投递不冒充完成 |
| 安静主动性 | Feed 静默，正常提醒回原聊天，封存期间转主对话，后台审批等用户打开头像 | 删除取消相关提醒；无事静默，预算及本机运行边界继续清楚 |
| 熟悉的身份 | Navi 专属形象承接助手详情，位置随当前页面变化 | 不复制 Muse 素材，不增加娱乐或角色定制能力 |

这些选择有代价。图标栏压缩空间却增加识别需求，因此必须做名称与触屏补偿。头像减轻主导航却加深记忆层级，因此在实际记忆回执中补直达入口。隐藏封存列表使界面安静，同时提高搜索和明确解封的责任。Feed 混排利于连续阅读，每帖仍需清楚说明来源与相关性。这些取舍要通过真实任务验证。

| 身份与记忆 | 身份内记忆入口、逐条管理、来源和生效说明、确认删除 | 记忆启停及对后续模型上下文的真实影响 |
| 成果库 | 草稿 / 文件区分、来源、下载与引用修改，统一简报入口 | 已有下载及导出状态，不改权限，不造影音类目 |
| 设置与高级区 | 基础连接检查、行为与预算、运行边界；协议、压缩、审计按需展开 | 密钥不回显、真实连接、已有工作流及严格策略 |
| Modal / Hover menu | 打开前记住触发点，关闭恢复焦点，Escape、背景关闭和提交规则明确 | 现有 reduced-motion 和焦点样式，补齐实际可操作性 |

Navi 专属形象首轮采用静态、清楚的小尺寸形象资产，可由后续视觉设计制作；该资产只承担身份及入口识别。不借用 Muse 角色文件，不将资产未定当成开发自行引入角色定制功能的理由。制作形象属于后续设计交付，本轮不生成素材。

**前端依赖，必须单独交代。** 当前接口未证明具备唯一主对话、封存 / 解封 / 删除、完整生命周期管理或 Feed 关注说明。当前通知以收件箱目标投递，不能仅把收件箱列表移入聊天就声称完成按创建会话路由。当前审批和作业列表也有数量上限，不能据此保证全部待审批均可发现。

后续需核对并补齐最小持久能力：主副类型和保护；标题、封存状态及明确解封；全量标题检索；提醒创建会话与实际投递会话；动作来源及版本；Feed 关注说明和本地生成时间；真实目标活动与成果关联。已有关系能复用时复用，缺关系时标明缺失，避免为了界面新增平行队列或另一套权限服务。

聊天解封和聊天保存目标需要真实运行时能力，不能依赖模型措辞模拟成功。Web 与 CLI 必须共用 Gateway 行为。提醒与审批呈现必须以获准和实际投递记录为准，不提前把待审生成内容写成已投递消息。关联关系、取消及删除事务属于后续实现依赖，本轮只定义产品约束。

## 6. 实施顺序与验收

Q01 和 Q02 已确认。后续获准开发后，先补齐会话生命周期、关联取消和持久路由，再验收删除、封存及提醒组合流程。下述四阶段均属于未来开发，不能把本次 Muse 测试或旧验收报告写成 Navi 的新完成记录。

| 阶段 | 修改目标 | 涉及范围 | 验收标准 |
|---|---|---|---|
| Phase 1 基础体验修复 | 让常见操作可预测、状态可信 | 更多菜单语义、重命名、标题范围与无结果、弹窗焦点、暂停来源反馈、统一简报动作 | 菜单打开不调用模型；保存后刷新持久；正文查询不冒充匹配；未检查不报成功；取消不改数据；Escape 回原触发点 |
| Phase 2 信息架构与归属 | 形成一致的助手使用结构 | 六入口、唯一主对话、删除与关联取消、封存与解封、助手四标签、身份记忆、目标三块、Feed 与提醒路由、审批持久呈现及必要持久关系 | 默认接回有效最近话题；主对话受保护；封存可通过标题搜索找回并明确解封；删除取消相关提醒；封存期间转主对话，解封后未来触发回原副对话；后台审批仅在侧栏；Feed 静默；并发与重启无重复投递 |
| Phase 3 视觉与交互细节 | 使日常阅读和小操作顺手 | 窄栏识别、Navi 形象、hover/focus 菜单、触屏、小屏侧栏、时间与字号、引用和结果入口 | 1280px、375px、320px 可用；键盘可完成导航和管理；按钮点击区足够；标签及状态可读；浮层不丢焦点；引用可移除；返回保留草稿与位置 |
| Phase 4 最终产品打磨 | 检验持续帮助与实际可靠性 | 真实委托闭环、重启恢复、并发审批、旧记录兼容、长历史与一周试用 | 一个持续事项能自然开始、修改、被提醒、处理审批、取用成果；状态可追溯且无重复执行；试用记录搜索与管理困难，B 未获用户选择前不实施正文检索 |

Phase 1 不先造新首页或新服务，优先修复已有体验断点。Phase 2 将必要持久行为与布局一并交付，避免只减菜单后失去控制入口。Phase 3 基于可用流程打磨，Phase 4 用真实使用修正产品判断。每阶段保持可运行版本，不用演示数据填补没有能力的部分。

| 关键验收场景 | 必须观察到的结果 |
|---|---|
| 第一次打开、返回昨天副对话 | 首次主对话可直接输入；返回恢复真实最近话题，无额外摘要调用 |
| 连续新建但未发消息 | 不不断留下空历史；已有主对话不被替换 |
| 重命名、封存、搜索、解封 | 标题持久；封存移出普通列表；无专用封存页；标题搜索可找回；明确解封后回列表 |
| 永久删除、取消删除 | 永久删除警告和关联提醒清单明确；取消无影响；确认后一并取消相关提醒及其未决工作；会话消息、摘要和搜索结果消失；主对话不能被绕过删除 |
| 删除与后台执行、投递同时发生 | 可取消工作停止，待审批和未投递动作失效；不可取消执行结束后再完成删除；无迟到投递、重建会话或重启复活 |
| 在不同会话设单次与周期提醒 | 正常回创建对话；封存期间只发主对话并标明来源；解封后未来触发回原副对话；已投递历史不搬动；切换页面和封存状态均不重复投递 |
| 正常与严格通知策略 | 正常提醒按授权投递；严格提醒先等待审批，获准后才形成投递消息；拒绝及旧版本不执行 |
| 原对话审批与无原对话审批 | 前者原回复和侧栏一致且持久；后者仅在侧栏；刷新、重启、重复点击不重复执行 |
| Feed 生成与显式订阅提醒 | 帖子混排静默；无聊天插话；只有已明确设置的提醒才按约定发往聊天 |
| 分类设目标、更新目标、看追踪 | 分类先讨论，保存后有真实记录；目标简述与实际进程一致；未要求时不自动创建提醒 |
| 查看 / 停用记忆、取用成果 | 从头像身份进入；停用确实影响后续上下文；成果下载真实，来源可回或明确缺失 |
| 无来源、暂停、模型故障、预算限制、休眠恢复 | 不报虚假成功；错误可理解；恢复与补做沿用现有边界，未发生的结果不展示 |

后续开发按 [AGENTS.md](../../AGENTS.md) 完成适合改动的测试和真实界面验收：默认入口 ./test，真实模型检查 ./test --live，分别记录结果。每阶段保留并实际验证 start.command、stop.command、status.command，确认脱离终端、关闭浏览器及重启恢复的行为。

验收使用独立测试数据，真实外部行动仍按审批，凭据不进入截图和报告。产品指标记录寻找入口、重复交代、话题找回、错投递和提醒价值等实际困难，无真实测量时不填改进百分比。测试通过不能替代产品任务验证。

**Q01 已确认：删除副对话时一并取消相关提醒。**

用户已于 2026 年 10 月 3 日选择方案 A。删除弹窗列出仍有效的单次与周期提醒，确认删除时一并取消，停止尚可停止的关联工作，使相关未决动作失效；不可取消执行结束后再完成删除。保留已完成的独立成果和必要执行记录。取消删除不改变提醒状态，取消范围不能扩大到其他会话。

采用理由：结束仍依附被删除话题的提醒，减少失去上下文的长期任务，避免悬空投递。继续提醒并转主对话的方案 B 不采用。Muse 没有给出确定删除规则，这项由用户为 Navi 单独决定，不能表述为对 Muse 行为的实测复现。

状态：产品方向已确认，相关实现和验收尚未执行。

**Q02 已确认：封存期间提醒转发主对话。**

用户已于 2026 年 10 月 3 日选择方案 A，作为 D08 正常路由的封存例外。提醒继续运行，已获准消息送主对话并标明来源为已封存话题，保留原始绑定和真实关联。解封后未来触发回原副对话，已投递历史不搬动或重复发送。以实际投递时的封存状态确定目的地，并记录真实去向。

采用理由：保留约定提醒的可见性，也对齐 Muse 的归档说明。封存对话不因投递自动解封或重新进入普通历史。副对话之后被删除时，Q01 的取消规则优先，原有转发停止。

权限边界：严格策略仍先审批再投递，提案明确原始绑定及封存期间的站内路由规则，防止实际去向与授权说明不一致。若行动内容或执行目标发生其他变更，按原规则重新审批。有来源待审提案仍保留原回复及侧栏索引，不因封存转成主对话提案；无来源后台审批仍仅在侧栏。

状态：产品方向已确认；Muse 实际转发送达仍未验证，Navi 后续独立验收封存、解封、执行中状态切换、防重复和重启恢复。

本计划当前没有等待用户决定的产品阻塞项。正文检索仍仅在用户未来选择 D02 的 B 后实施，真实连接器与新增通知渠道另议。

其余布局尺寸、文案、菜单焦点和静态形象的制作可在已确认方向内做常规设计。若后续提出主导航变化、正文搜索、真实连接器、权限变化或新的通知渠道，需要重新确认；本轮不预先采用。
