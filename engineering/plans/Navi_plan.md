## 1. 项目目标与范围

项目最终名称为 **Navi**。MiniClaw 仅用于引用原始课程要求，产品界面、项目文档和运行入口统一使用 Navi。

Navi 是运行在用户本机的个人 AI 助理系统。它应理解并持续使用用户的偏好、记忆、目标和会话，执行定时任务与 Heartbeat 检查，在出现值得关注的信息时主动提醒，并在外部行动或高影响操作前取得用户批准。

最终交付必须同时达到两组目标：

- 完整覆盖原始 MiniClaw 的 Basic 70 分与全部 Advanced 30 分要求，并提供可复现的验收证据。
- 对齐 Muse 的核心个人助理体验，包括聊天、记忆、目标跟进、动态消息、个性化建议和轻量成果库，同时完成前端视觉与交互打磨。

MVP 是阶段性成果。最终交付须完成本计划规定的全部范围。

## 2. 产品体验与 Muse 参考方法

Codex 应主动打开本机 Muse，观察相关产品流程和视觉表现。观察应发生在开发开始时，以及主要功能和界面完成之后。

对齐重点包括：

| 产品部分 | Navi 应实现的体验 |
|---|---|
| 聊天 | 连续会话、流式反馈、清晰的执行进度，以及从明确指令创建记忆、目标和任务 |
| 记忆 | 用户可查看、修改、删除，并控制记忆是否参与后续回答 |
| 目标 | 保存目标、状态和下一步，关联任务与成果，支持持续跟进 |
| 动态消息 | 展示有来源、有时间信息、与用户关注事项有关的更新 |
| 个性化建议 | 根据记忆、目标和未完成事项提出具体建议，并解释建议依据 |
| 成果库 | 保存、查看和下载实际生成的简报、文档等成果 |
| 审批与活动 | 清楚展示待批准的动作、执行结果、失败原因和关联记录 |

默认主界面以聊天为中心。今日摘要、目标、动态、建议、任务和审批应容易进入；开发诊断信息放在专门的状态与审计界面。

前端应参考 Muse 的布局、留白、文字层级、配色、间距、圆角、导航和交互反馈。Navi 保留自己的名称与视觉身份。

Codex 可自主选用已有 UI、美化及其他相关技能，必要时查找并添加适用技能。新增技能应记录来源和用途。开发辅助技能与 Navi 运行时的 Skill/MCP 扩展分别验收。

遇到以下情况，应尽早与用户讨论，再确定是否对齐：

- 功能实现成本明显超出收益。
- 需要复杂基础设施、额外账户或大量持续维护。
- 观察到的执行效果不稳定，或只有建议文案，缺乏实际效果证据。
- 功能会明显增加等待、费用或操作负担。
- 功能对个人助理的核心体验帮助有限。

主要页面完成后，必须在相同窗口尺寸下与 Muse 进行截图对照，并检查真实数据、加载、空白、错误、长文本和窗口缩放状态。视觉检查与关键交互验证通过后，才能声明前端完成。

## 3. 提醒、权限与审批

Navi 将动作分类并由确定性的权限规则执行。模型不能自行决定绕过审批。

| 动作类别 | 默认处理 |
|---|---|
| 分析、生成草稿、维护系统内部状态 | 自动执行 |
| 向用户发送普通信息提醒 | 根据用户授权自动发送 |
| 修改外部系统、向第三方发送消息、发布内容、写入用户可见目标文件 | 执行前审批 |
| 高影响操作或敏感信息外发 | 执行前审批 |
| 类型或授权范围无法确定 | 暂停相关动作，请用户确认 |

普通提醒默认投递到 Navi 站内消息。若增加本机系统通知，应由用户明确启用。邮件、第三方聊天平台等外部投递渠道需要单独授权，不能由普通提醒权限自动覆盖。

审批必须发生在产生副作用之前。待审批动作应显示具体内容、目标和预期影响。修改内容或目标后，重新审批修改后的动作。

拒绝的动作不得执行。审批决定和实际执行必须关联到同一份动作内容。

统一流程为：

```text
Agent 产生结果或动作草案
        ↓
保存草案与动作提案
        ↓
权限策略判断
        ↓
已有授权的普通提醒自动获准
或等待用户人工审批
        ↓
获准结果进入本地 Outbox
        ↓
Delivery 执行
        ↓
保存投递状态与审计记录
```

保留两种可见、可切换的通知策略：

| 策略 | Heartbeat 普通提醒 |
|---|---|
| 日常使用策略，默认 | 自动获准并投递，记录授权依据 |
| 严格逐条审批策略 | 每条提醒等待用户批准，批准后进入 Outbox |

原始 PDF 明确要求 Heartbeat 通知发送前审批。验收应使用严格策略演示批准与拒绝的完整流程；日常默认策略的差异必须在文档和证据中明确标注。课程评审是否接受这种可切换策略，应如实说明，不能保证对应评分。

两种策略共用同一 Gateway、权限服务、Outbox 和持久化实现。严格策略须实际执行，不能通过模拟审批代替。

## 4. 技术路线与运行边界

采用本机单用户 Web 应用：

| 部分 | 方案 |
|---|---|
| 后端 | Python 3.12、FastAPI |
| 持久化 | SQLite |
| 前端 | TypeScript、React、Vite |
| 模型服务 | DeepSeek 真实 API，通过独立 Adapter 接入 |
| 通道 | CLI Adapter 与 Web Adapter |
| 正式运行 | 单一 Gateway 进程，提供 Web 界面并管理后台任务 |
| 默认入口 | `http://127.0.0.1:8766` |

核心服务作为同一应用中的模块实现。先采用直接、清楚的模块接口，控制依赖和抽象数量。

前端构建后由后端提供。阶段性交付时应准备好前端产物，用户无需分别启动后端和 Vite。

DeepSeek 接入应在开发初期验证真实模型响应、工具调用和工具结果回传，并记录通过验证的接口、确切模型名和配置。官方英文仓库也明确区分模型目录与实际端点可用性，因此不能仅凭目录或旧示例认定接入成功。[DeepSeek 官方英文实现参考](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/llm/llm-deepseek/README.md)

密钥由用户在本机配置。不得从其他项目读取，不得进入源码、版本控制、运行证据、截图或普通日志。

默认调用限制：

- 单次模型请求超时：60 秒。
- 单个 Agent 作业执行期限：180 秒，不包含等待人工审批的时间。
- 单作业最多 5 次模型请求、10 次工具调用。
- 单次模型输出最多 4096 tokens。
- 每日最多 100 次模型请求及 100000 总 tokens。
- 重试、会话压缩和后台建议生成均计入预算。

记录实际 usage，并根据核实后的费率估算费用。达到预算限制后停止新调用，保留任务并显示原因。用户可以在设置中调整限制。

本机后台工作的边界必须明确：

- 关闭 Web 页面不停止 Gateway。
- 通过便捷启动器启动后，关闭启动终端窗口不停止 Gateway。
- 停止 Gateway 或电脑休眠期间，不执行检查。
- 恢复运行后保留历史状态；对每个调度最多补做一次最近错过的检查，并记录遗漏区间。
- 不连续补跑大量错过的周期，不重复执行同一到期作业。

技术参考：[FastAPI 部署概念](https://fastapi.tiangolo.com/deployment/concepts/)、[Vite 官方指南](https://vite.dev/guide/)。

## 5. 核心工程实现

Gateway 是统一入口，负责身份、会话、任务编排、权限与持久状态。CLI 和 Web 必须通过各自 Adapter 访问它。

```text
CLI Adapter ─┐
             ├→ Gateway → 会话、记忆、目标、任务与调度
Web Adapter ─┘                ↓
                         Agent Adapter
                              ↓
                         Skill/MCP 扩展
                              ↓
                         结果与动作提案
                              ↓
                         权限与审批
                              ↓
                         Outbox → Delivery
```

持久化至少覆盖用户、会话与消息、记忆、目标、任务、周期调度、Heartbeat 设置、作业与尝试记录、扩展调用、审批、Outbox、投递、上下文摘要及审计记录。

记录之间应通过稳定 ID 关联。调度修改影响未来触发，保留已有作业的执行配置和历史。

作业应有可见的等待、运行、成功、失败、取消和超时状态。审批状态与投递状态分别记录，避免将“生成成功”显示为“行动已完成”。

同一调度的同一次到期事件只创建一个作业。重试作为该作业的新尝试保存。初始最多自动重试两次，仅重试可恢复错误；已取消作业和可能产生重复副作用的动作不得盲目重试。

重启后应恢复未完成工作的明确状态。投递结果无法确认时，记录不确定状态，等待核查。

首个运行时扩展采用实际可执行的本地简报 Skill，读取固定格式的检查条目并返回结构化结果。另提供具有相同接口、采用不同筛选规则的替代 Skill。

Agent 必须实际加载扩展说明、调用扩展，并使用输出生成结果。通过配置切换扩展后，应展示结果变化，无需修改 Gateway 路由。运行中的作业保留原配置，后续作业使用新配置。

长会话压缩应保存会话目标、关键事实、未完成工作和待审批动作的引用。压缩后继续原会话，保持原会话 ID。原始历史仍可追溯。

记忆管理应实际影响后续检索和回答。删除或禁用的记忆不得继续从缓存参与回答。

动态消息必须携带来源与时间信息。无法获取或验证的信息应显示失败或不确定状态。搜索使用非中文网站信源，结果标注来源，优先采用官方或第一手资料。

## 6. 启动、关闭与阶段性交付

每个可交付阶段必须提供以下入口：

| 入口 | 行为 |
|---|---|
| `start.command` | 双击启动后台，检查就绪后自动打开 Navi |
| `stop.command` | 双击优雅停止本项目 Gateway |
| `status.command` | 双击查看运行状态、正确网址和日志位置 |
| `./run` | 前台运行 Gateway，用于开发与课程演示 |
| `./test` | 执行默认离线自动测试 |
| `./test --live` | 显式执行真实 DeepSeek 接入检查 |
| `./navi` | 通过 CLI Adapter 操作同一 Gateway |

启动器必须从自身位置定位项目，支持路径中的空格和中文。重复启动应复用已运行的 Navi，避免重复后台进程和调度器。

端口被其他程序占用时，应说明原因，不能终止其他程序或打开错误应用。

便捷启动器必须让 Gateway 脱离启动终端，并将输出保存到日志。停止入口只操作本项目拥有的进程。停止时暂停领取新工作、处理运行中的作业状态并保存数据。

首次配置应提供清楚的依赖准备和 DeepSeek 配置流程。后续启动尽量做到双击即用。

每次阶段性交付都必须向用户说明：

- 双击哪个文件启动，以及正确访问地址。
- 首次启动是否需要准备依赖或配置密钥。
- 启动完成后，启动终端窗口可以关闭。
- 关闭浏览器页面或启动终端，后台仍继续运行。
- 真正停止后台应使用 `stop.command`。
- 使用前台 `./run` 时，需要保持终端；按 `Ctrl+C` 正常停止。
- 重启后保留哪些状态，以及如何查看运行状态和日志。

这些说明必须根据实际测试结果编写。必须亲自验证启动、关闭启动终端、重新访问、停止和再次启动的完整过程。
