## 推荐实施方式

最小方案是在现有 Gateway、SQLite 和前端组件内补齐缺口，复用既有生成、卡片、弹窗与终止机制。推荐采用这个方案：新增服务、运行时、账号、公开环境变量和 CLI 命令均为 0。现有 Python 3.12/FastAPI/SQLite、React/TypeScript/Vite 和真实 DeepSeek 接入保持一致。

本版有五个可分别交付的阶段，涉及超过 8 个源文件。保留原 V2-01 至 V2-04 编号，新增 V2-05 图文动态与并排讨论，四项日志缺陷在 V2-01 先修复。每阶段完成后产品均可独立使用；来源扩展尚未完成时使用现有三个来源，全文搜索尚未完成时标题搜索仍可用。预计有效实施与验证约 6 至 9 个工作日，真实次日定时与休眠后观察另占自然时间。最易影响进度的是公开源正文与图片差异、休眠行为以及个人数据迁移。

旧计划的四项调整继续保留：标题与正文搜索、公开 RSS/Atom URL、默认解除本地日预算拦截、类别说明确认。此次增加网络与休眠恢复、动态正文与配图、动态并排讨论、搜索打开和关闭细节。用户已确认全文搜索范围及“优先真实来源图片，无图时保留彩色图标和正文”；其余推荐随 v2 审核。复杂影音、交易、点赞系统、额外模型或图片生成服务均不纳入。

本计划假设真实 DeepSeek 和至少一个启用的公开订阅源能正常访问。如果这个假设失效，新内容无法可靠生成；设计通过保留最后一个成功批次、展示具体失败来源和下次计划时间维持可用性。不得声称云端停机、欠费或网络故障时仍能保证新内容产出。

开窗只播放一次 160ms ease-out：opacity 0 到 1，scale 0.97 到 1；外框布局尺寸自始固定，不做高度扩张动画。`prefers-reduced-motion` 下直接完整呈现。160ms 是拟定实现值，未宣称是 Muse 实测时长。字体、图标与滚动条变化也不能改变弹窗轮廓。

选择上述直接查询以避免新增全文索引同步与迁移。调查时用 2000 会话、100000 条约 600 字符的合成消息做只读内存 SQLite 原型，稀有词与未命中查询约 247 至 260ms；它只证明基本路线可行，没有测量完整 API 和片段计算。正式验收在同等规模数据上对完整 API 测 p95 ≤ 500ms，并记录实际测试机与样本。当前个人数据仅 7/34，不能据此声称大规模性能已验收。

接近的替代方案是 FTS5 trigram 索引，但短于三个字符的 MATCH 存在限制，也增加外部内容索引一致性工作。本版先采用直接查询。若正式完整查询超过上述指标，交付前先调整同会话命中查询与分页，仍无效时暂停该阶段，提交实测与具体索引方案供审核，不能静默增加搜索服务。

验收覆盖正文独有词、中文一字/两字、标点、英文大小写、多条命中合并、标题优先、分页、归档、删除竞态、空查询及无结果。搜索前后 usage 和模型请求数不增加，命中定位正确，关闭返回原页面及原输入状态。

在 Safari 与 Chromium 检查：鼠标打开再点遮罩、输入查询后鼠标关闭、键盘打开再 Escape、键盘打开后鼠标关闭，以及下一次 Tab 导航。D19 的截图现象未在本次简单鼠标流程重现，实施必须覆盖这些组合并记录结果，不能声称已确定唯一原因。D20 将 API 响应延迟一秒，分别用 0、1、20 条近期话题、无结果和错误，连续打开三次；记录首帧、动画中与加载后的 layout 宽高，差异不超过 1 CSS px，scale 的视觉变化单独记录。桌面与窄屏均无输入栏先单独出现再撑高外框的过程。

### V2-04 手动来源管理

新增能力限定为用户明确填写的公开 HTTPS RSS/Atom 订阅 URL，可预览、确认、暂停与恢复；普通网页 URL 若返回 HTML，要明确提示需要订阅地址。本版不扩展到登录站点、通用爬虫或自动猜测新闻来源。此处是对“手动可控”的最小可执行解释，用户审核本版时可调整这一边界。

修改 `backend/navi/feeds.py`、`web.py`、`gateway.py`、前端来源弹窗和 `data.ts`。新增 `backend/navi/feed_http.py` 专门完成自定义 URL 的公开目标连接校验；使用现有 HTTPX/httpcore，不新增依赖。

保留三来源预设、ID 和开关。右上角“管理来源”内新增订阅地址、可选名称、预览、确认添加。名称最多 80 字符，URL 最多 2048 字符。预览展示站点域名、订阅标题及最多三条最新文章的标题和日期；预览成功后确认才保存。用户改 URL 后清除旧预览并重新检查，不允许把 A 源预览与 B 源保存混用。新增来源只影响之后的自动批次，不另设生成按钮。

新增 `POST /api/feed-sources/preview {url}`，返回规范 URL、订阅标题、最近三条条目。扩展现有 `POST /api/feed-sources`：接受原 `source_id`，或自定义 `url` 与可选 `title`，两种输入互斥；确认添加时再次实际验证地址与可解析内容，避免仅信任浏览器预览。重复规范 URL 返回已有来源，不重复订阅。原 toggle API 继续复用。输入和不支持格式返回 400，目标读取失败返回 502；响应只保留可读原因，不泄露认证信息。

沿用 records(kind=source) 存储，payload 增加 `source_type=builtin|custom`，旧记录缺少此字段时按 builtin 读取；自定义 source_id 为 `custom-` 加规范 URL 的 SHA-256 前 24 位，record ID 为 `source-` 加 source_id，保存 url/title/enabled/last_checked/last_success/last_error。预设 ID 保持不变。URL 规范化只统一主机大小写、默认端口和移除 fragment，保留大小写敏感路径与实际查询参数。来源正文、文章与日期都以真实解析结果为准，不能用模型推断缺失信息。

解析器同时支持 RSS 2.0 与带命名空间的 Atom 1.0，沿用 ElementTree。RSS 时间按现有 RFC 日期解析，Atom 按 ISO 8601 解析。文章有有效链接与发布时间才可进入已验证材料；跳过无效条目，全部无效时返回无可验证条目的错误，不能把它保存为成功源。条目相对链接按实际订阅 URL 解析，输出链接限定 http/https。详情摘要清理 HTML 与控制字符并保持长度边界。来源文本只是数据，不能改变指令、工具权限或审批。

自定义 URL 只接受 HTTPS 443，无用户名或密码。连接前校验 DNS 解析得到的所有地址属于公开可路由地址，拒绝 loopback/private/link-local 等本机或内网目标；连接固定到经过校验的地址，TLS 仍验证原始主机名。`feed_http.py` 通过现有 httpcore 网络 backend 包装 connect_tcp 完成此约束，不先检查后另做一次不受控解析。自定义读取禁用重定向与环境代理，保持 TLS 校验；重定向提示用户填入最终订阅 URL。预设来源继续使用已有路径。此边界只用于用户提供的 URL，不影响本机 Gateway 通信。

保留单源 12 秒和 2MB 读取边界。自动刷新至多并发 3 个来源，总刷新窗口 60 秒；超出窗口的源显示未完成，模型只使用已成功验证的材料。单个来源失败不清空其他来源材料，不把失败源记为已访问成功。人工预览和确认不调用模型。暂停源不参与后续抓取，恢复沿用原 ID；本版不增加来源硬删除入口。

验收使用 RSS/Atom 固定样本验证格式，现有预设验证兼容，官方 GitHub Blog feed 作为新增公开来源样本实际检查。必须覆盖重复 URL、预览后改地址、HTML、损坏 XML、缺失日期、超时、超大响应、重定向、内网地址、DNS 地址变化和一个失败源与一个成功源并存。不能以 web 工具无法解析 RSS 文本为来源不可访问的证明，须保存实际 HTTP 与 XML 校验结果。

### V2-05 可刷阅的图文动态与左侧讨论

本阶段对应 D18。最小做法是扩展现有生成材料和 feed payload，完整渲染正文，用真实来源图与评论式按钮呈现，再将已有 ChatPanel 放到动态左侧。采用这个方案，不引入图片生成模型、新闻爬虫服务或新前端框架。新增 `frontend/src/FeedPanel.tsx` 集中处理动态列表、翻页和图片；修改 `App.tsx`、`App.module.css`、`ChatPanel.tsx`、`data.ts` 及 `backend/navi/feeds.py`、`agent.py`、`gateway.py`、`web.py`，复用 V2-04 的 `feed_http.py`。本阶段只有旧三个来源时也可交付。

正文改为通常 140 至 300 个中文字符，约两段，交代发生了什么、具体变化和与关注方向的关系，避免重复标题后只补一句。这个区间是对 Muse 信息密度的实现目标，缺少事实材料时允许更短，不能为凑字数编造。现有 feed 校验的正文上限 1000 保持，构想正文与五条规则不变。列表移除 `.slice(0,220)`，直接显示完整正文，复用 ReactMarkdown 的段落和短列表；默认不解析原始 HTML，feed 正文禁用 Markdown 远程图片。正文不接受模型自编 URL，来源和图片由后端真实资料组装。

当前 RSS description 先被截断到 180 字符，模型 prompt 又要求简短且声明只读摘要，这共同限制了正文。解析优先使用 RSS `content:encoded`、Atom content，其次 description/summary，清理成文本，每条最多 2000 字符；一次模型输入最多 12 条材料、材料正文合计最多 24000 字符，按发布时间排序且每源最多三条。仍不足 400 字符或缺少来源图时，最多读取五条候选材料明确提供的公开原文链接，用标准库 [HTMLParser](https://docs.python.org/3.12/library/html.parser.html) 提取 article/main 正文及 [Open Graph 图片元数据](https://ogp.me/)，不能遍历其他链接、登录或执行网页脚本。只有实际提取到文章正文才标 `read_scope=article`，仅取得图片或元信息仍按 rss。RSS 刷新保持 60 秒窗口，原文补充并发最多三条、单篇 12 秒/2MB、整体 30 秒，失败即沿用实际 RSS 材料。`read_scope=rss|article` 与实际读取时间进入来源元数据，prompt 按每条真实读取范围描述；这明确扩展了旧版仅使用 RSS 摘要的边界，不能把未读取网页写成已阅读全文。

配图按用户确认的策略：优先文章对应的 RSS/Atom 图片附件、Media RSS thumbnail/content、订阅正文中的图片，再用实际原文页的 `og:image`；每条最多一张代表图，无可用图时仅保留彩色图标和正文。只采用该条实际 source_ids 对应材料的图，不将同一张来源站点 logo 铺到每条，也不从无关搜索结果补图。来源支持的尺寸、说明和 URL 随图保存，缺失 alt 时用对应文章标题。没有声明尺寸时先预留 16:9 媒体区域，加载后也不突然改变外框；有实际尺寸则使用其比例。可点击查看大图，复用现有 Dialog。

feed payload 增加 `icon_key` 与 `images[]`，旧记录缺少字段时使用通用图标与空数组。`icon_key` 限定 ai/code/space/science/learning/general，复用现有图标库与六组固定颜色，图标约 32px；不接受外部 SVG 或任意颜色指令。图片元数据含 `asset_id`、`source_url`、`alt` 以及可选 width/height，asset_id 是规范图片 URL 的完整 SHA-256。模型最多选择枚举图标，不能提供图片 URL；后端根据已校验 source_ids 绑定真实图片。

新增 `GET /api/feed-media/{asset_id}`，只接受已发布动态引用过的 64 位十六进制 ID，由存储资料反查实际来源 URL，不能接受任意 URL 参数。实际图片读取沿用公开 HTTPS 目标与连接固定校验，无第三方 Cookie、认证或重定向，12 秒/5MB、并发最多三张，仅响应 JPEG/PNG/WebP/GIF，拒绝 HTML/SVG 等内容。响应使用浏览器私有缓存一天，不增加二进制数据库、长期磁盘图库或后台图片作业。页面懒加载，读取失败显示简短无图状态并保留图标、正文与来源，不使整个 feed 失败。图片读取与分页均零模型调用。

页面按本地生成日期分组，正文区域最大宽约 780px，标题左侧放彩色简约图标，正文约 16px/1.65 行高，以留白分隔条目。保留一个简洁真实来源入口，把重复来源、生成时间、源发布时间和检查时间移入每条“来源与时间”详情，避免技术信息占据正文前后。图片位于正文与讨论入口之间。用 MessageCircle 图标加“讨论”替换“带引用讨论”，呈现接近 Muse 的评论入口，不增加点赞系统。旧标题详情与引用 ID 仍有效，列表可以直接读完内容。

连续浏览使用 `GET /api/feed/items?limit=20&before=<cursor>`，返回 `{items,next_cursor}`，按 created/ID 降序稳定游标，每次最多 50 条；cursor 为 URL-safe Base64 编码的 `[created,id]`，不超过 256 字符，无效参数返回 400，查询使用绑定参数。只包含可见 generated 动态，排除原始订阅材料。靠近列表末尾 300px 加载下一页，并保留可操作的“加载更多”，错误可重试且不清空已读条目。Web 状态轮询使用新增可选 `feed_limit=20`，仅限制快照中的 feed；原状态 API 不传参数时保持全量，CLI 与其他 record 类型兼容。已翻页条目由 FeedPanel 保存，轮询刷新不把列表缩回第一页，不重复 ID。新批次和开关聊天均保持当前阅读条目的滚动锚点，不加新模型请求。

点击讨论时 `#feed` 保持不变，右侧仍是当前动态，左侧打开 ChatPanel，桌面初始约 40% 聊天、60% 动态。优先恢复当前普通活动聊天；若当前为归档或目标引导会话，则使用已有 main 会话，避免把新闻讨论送进目标创建流程。不为每条动态自动建新会话，不自动发送、不预填指令、不触发模型。输入原有草稿与其他引用保留，条目引用放入待发送区，明确“正在回复 Navi · {标题}”并可移除。再次点击另一条只替换此次待讨论的 feed 引用；引用达到现有五条上限时明确提示用户移除一条，不静默丢弃旧引用。

引用继续使用原记录 ID、正文和 source_ids；用户发送时才走现有聊天 API，由 Gateway 重新验证引用。动态在发送前失效时提示并保留草稿，不能绕过引用校验或工具审批。ChatPanel 的同一按钮可收起、打开并排或展开完整聊天，回到并排后动态阅读位置与聊天位置保持。抽出目标与动态共用的布局状态，但不合并两个业务生命周期；目标引导 API 仍只在目标页执行。窄屏用动态/聊天切换保留引用、草稿和滚动位置，避免挤成两窄列。

验收以 B18/C18/F18 及本次实际点击为依据：相同内容区域尺寸下对照条目密度、图标、段落、配图、讨论按钮与两栏结构。中性真实来源分别覆盖有图、无图、图片 404/超时/错误 MIME、短摘要与原文不可读；图片来自对应文章并可核对出处。至少三条事实材料充足的真实动态达到正文目标，来源确实支撑其事实。用三页以上条目验证连续浏览、失败重试、轮询和开关聊天不丢阅读位置。点击讨论前后 jobs、messages、sessions 和模型用量不增加，草稿原文不变且引用可移除；只在人工发送中性问题后产生一条实际聊天及 receipt。桌面与窄屏均验收，不能用静态截图代替交互闭环。
